# Tidehaven：独立游戏与星露谷模组路线比较

调研与试验更新：2026-10-30。用户已批准最小隔离原型，原生LAN双进程、扩建、横版潜水、箱子交矿、过夜和重连已取得本地受控证据，详见[样板报告](implementation-stardew-spike.md)。完整路线成本仍是工程判断，不是工期报价；未决定全量迁移。人物方向已确认“架空近代中国海港，以民国劳动服饰为参考”。

## 结论先行

**现阶段建议继续评估“原生岛上生活与甲板＋自定义横版潜水”的SMAPI代码模组。** 最小样板证明了原生LAN、分场景、扩建和横版接入可行，也发现库存必须按持有者权限实现预约／回执；它还没有证明全量迁移更便宜。不能把“双人自由分工”当作独立游戏独有优势，或预设Mod必须放弃横版。10月29日的初判由此更新。0.18保持可玩基线，试验不等于启动第二款完整游戏。

用户最在意尽早得到稳定、好看的可玩版本。岛上复刻成熟生活玩法时，模组确实能省掉大量底层和原作已有美术工作，不应因已经写了Godot代码就忽略它。反过来，把横版动作与动态船只塞进原作，也不能按普通内容包估成本。

## 先分清三种路线

| 路线 | 能复用什么 | 还要承担什么 |
|---|---|---|
| 以Content Patcher为主的内容Mod | 原生种植、城镇、NPC事件、物品、商店和联机 | 新人物/地图/剧情；完整航行与横版战斗超出普通内容包范围 |
| SMAPI代码Mod＋内容包 | 上述生活系统、联机会话与消息运输；海上玩法可以自行编程 | 木筏状态、侧视控制/战斗、原生库存与时钟桥接、版本兼容；这是本次值得试验的中间路线 |
| 继续Godot独立游戏 | 现有0.18海上/水下规则和本地可玩成果 | 全部生活系统的品质、动画/音效、内容密度、邀请联机与分发体验都由项目维护 |

这里的“代码Mod”仍可保留原生联机，不需要再造Socket/ENet连接层；普通C#字段却不会因此自动同步，必须明确哪些用原生实体/网络字段，哪些用主机消息。

## 10月30日补充证据：联机应计入Mod的优势

1. 原作已有Steam/GOG邀请、邀请码和LAN入口；主机持有完整世界，客机同步当前等活动地点。两人在不同地点本来就是受支持的结构。`Data/Locations`还有`AlwaysActive`，允许指定地点无人进入时仍向客机同步；它不保证自写航行/战斗会自动模拟。[原作联机说明](https://www.stardewvalley.net/stardew-valley-v1-3-beta/)、[地点与客机世界](https://wiki.stardewvalley.net/Modding:Modder_Guide/Game_Fundamentals#Farmhand_shadow_world)、[地点配置](https://wiki.stardewvalley.net/Modding:Location_data#Basic_info)
2. **Fishing Trawler – New Horizons**作者明确支持联网及本机分屏，玩家可以在甲板、船底等区域协作修船/补网/维护发动机。源码对出航、修复事件和状态分别发送Mod消息。这是已有可发布的海上多人玩法，不能说Mod无法承载船上分工。但它的限时捕鱼航程不等同于自由驾驶、逐格扩建和持久船屋。[作者页](https://www.nexusmods.com/stardewvalley/mods/15941?tab=description)、[同步源码](https://github.com/Floogen/FishingTrawler/blob/development/FishingTrawler/Framework/FishingTrawler.cs)
3. **Swim**已有水域移动、下潜、资源/宝箱、湖底矿物及氧气。它能减少俯视潜水方案的起步工作；现有证据没有证明横版鱼叉战斗或完整双人存读链。原版和Continued是不同分支，不能混合计算功能与兼容承诺。[Swim](https://www.nexusmods.com/stardewvalley/mods/6326)、[Swim – Continued](https://www.nexusmods.com/stardewvalley/mods/23169)
4. **DoomValley**的`IMinigame`源码具有独立更新、绘制与输入，足以证明模组可采用不同视角；**Sled Valley**作者同时明确区分多人环境中各自游玩与同场比赛。这些只证明扩展能力，不证明我们的横版协作已经解决。[DoomValley源码](https://github.com/wojciech-graj/DoomValley/blob/master/DoomValley/DoomMinigame.cs)、[Sled Valley作者页](https://www.nexusmods.com/stardewvalley/mods/53778)
5. **Magical Fishing Raft**是建筏并切换钓点的实例，但作者明确不能离筏、不能摆物件。它不能直接替代当前动态基地；没有找到完整同规格成品，不等于技术上做不到。[作者页](https://www.nexusmods.com/stardewvalley/mods/22284?tab=description)

以上只读核查，截至2026-10-30，未亲自运行这些模组。实例可用于体验参照，复制代码/素材或重新打包需分别遵守其来源条件；本轮未引入第三方模组依赖。

## 值得验证的实现方案

下面是工程方案，不是已经实现的能力：

- **甲板本地坐标＋海图坐标**：甲板是一个原生地点，箱子、设施、人物使用相对甲板的位置；另记录船在海上的位置和航向，驱动海面、漂流物、航行碰撞和登岛入口。船仍能真实航行，不必每帧搬动所有家具和玩家，也不等于固定船屋传送菜单。
- 扩筏由主机更新合法甲板格集合与版本号，各端重建显示和碰撞。不能假定修改本机xTile地图会自动同步；原生箱子/库存尽量直接复用。保持现有停泊、同伴返筏才启航等规则，不为试验新增“一人下潜同时开船”。
- 岛上使用原生地点、种植、事件和NPC系统；横版潜水可用独立控制/绘制模块，通过SMAPI消息传输入和状态。主机模拟与其正在看的场景分离，双方均可下潜；进入退出、全局时间、背包、奖励与存档需要专门桥接。
- 另一方案是将海底也保留为原生地点，并只在该地点替换移动、碰撞和绘制。它可多复用位置同步，却更依赖原生人物/工具内部实现。两种方式都不应在未经小样验证时宣称更省。
- `CreateOnLoad.Type`不能随意填自定义类并期待原生序列化；首个试验优先原版`GameLocation`。持久状态使用主机存档/实体`modData`，高频运动用有界消息，不每帧广播整个JSON。[地点类型限制](https://wiki.stardewvalley.net/Modding:Location_data#Basic_info)、[数据API](https://wiki.stardewvalley.net/Modding:Modder_Guide/APIs/Data)、[消息接口](https://github.com/Pathoschild/SMAPI/blob/develop/src/SMAPI/IMultiplayerHelper.cs)

## 试验的决定标准

先做一小段：**两人上船 → 放箱子/扩一格 → 航行停泊 → 一人留甲板、一人横版下潜 → 取得一种资源并交给同伴 → 睡眠保存、退出、重连**。主客交换岗位、两人同时下潜以及断线返航也要查。只测接口存在或单人会动，不足以决定迁移。

| 观察结果 | 对路线的影响 |
|---|---|
| 原生岛屿/库存/联机确实保留，横版和船的改动集中，操作能达到要求 | 倾向继续Mod，再逐条迁移人物/剧情；不一次搬全量内容 |
| 仅靠简化核心玩法才能成立 | 先向用户明确差异；当前核心没有获准自动删减 |
| 经试验仍需大量全局补丁、同一状态保留两套冲突模型、存读/重连持续不稳 | 倾向继续Godot，收紧内容范围并打磨0.18 |
| 用户要求脱离星露谷本体独立启动/发行 | 产品形式直接倾向独立游戏，不再以内容Mod估算 |

比较应以“从今天到稳定成品的剩余工作”为准：Godot已有代码能否保留有实际价值，但沉没投入不是选路线的充分理由；Mod省掉的成熟生活系统也必须扣除移植、桥接和版本维护成本。目前不报虚构百分比或保证工期。

## 本机准备状态（只读核对）

- 已找到`C:\SteamLibrary\steamapps\common\Stardew Valley`：游戏DLL产品版本1.6.15，SMAPI DLL版本4.2.1；.NET SDK 8.0.424存在。
- 该目录当前只有`Content`子目录，没有`smapi-internal`或`Mods`。因此只能确认SMAPI文件存在，**不能确认完整安装或能启动**。未运行启动器、改Steam配置、安装/修复依赖或访问个人游戏存档。
- 实际试验前需准备隔离模组目录与测试存档并核验安装完整性。本轮完成研究和验收方案，尚未创建Mod工程或决定迁移。

## 查到的能力与限制

- Content Patcher作者指南明确支持替换图片、对白、地图，添加物品/果树/地点和修改商店库存，内容可按条件变化。因此人物、作物、配方、对白与岛屿地图是适合复用原作系统的部分。[作者指南](https://github.com/Pathoschild/StardewMods/blob/develop/ContentPatcher/docs/author-guide.md)
- Ridgeside作者项目已有新NPC、地图、音乐与事件，能作为“扩展一个有丰富人物关系的小镇”的内容组织参照；这证明模组路线可容纳大量故事，不代表它们可不经适配直接成为本作内容。[作者仓库](https://github.com/Rafseazz/Ridgeside-Village-Mod)
- Swim作者页面提供游泳、潜水寻宝等功能。查阅时显示4.0.2、2026-10-16更新；这说明不能笼统断言星露谷无法做潜水。本次没有实测其当前双人兼容，也没有证据证明它等同于我们要的横版鱼叉/躲避/采矿与动态筏循环。[作者发布页](https://www.nexusmods.com/stardewvalley/mods/6326)
- SMAPI提供代码加载、事件与API；多人接口可向指定玩家/模组发送数据。自定义氧气、钩子载货、船上建造和奖励仍要设计同步与存读，接口存在不等于规则自动正确。[SMAPI项目](https://github.com/Pathoschild/SMAPI)、[多人接口源码](https://github.com/Pathoschild/SMAPI/blob/develop/src/SMAPI/IMultiplayerHelper.cs)
- 跟教程时要留意版本：Content Patcher旧`CustomLocations`字段已被作者标为弃用，1.6及以后应使用游戏原生Location数据方式；不能照搬老示例建立新项目。[作者弃用说明](https://github.com/Pathoschild/StardewMods/blob/develop/ContentPatcher/docs/author-guide/custom-locations.md)

## 对我们每类玩法的影响

下表为基于上面证据和当前代码的工程推断，低/中/高表示相对新增工作，不是已测试结果。

| 需求 | 继续独立游戏 | 星露谷模组 | 取舍 |
|---|---|---|---|
| 岛上农耕、作物、钓鱼、矿洞 | 当前有首版，后续品质与数量需自己维护 | 大量原作规则和反馈可直接沿用，新增内容较省 | 模组明显占优于重做同类基础系统 |
| NPC、日程、关系、长剧情 | 已有短篇和日程，需补事件演出和长期反应 | 原作交谈/日程/事件基础成熟，仍需写文稿、角色图和验证条件 | 模组能省框架，不能省内容创作 |
| 中国古代/民国人物 | 扩配套角色、动作、肖像及换装；控制自由 | 可替换/扩展图像与人物内容，也需配套动作和肖像 | 两者都需要美术设计；改发色不解决风格 |
| 寿司店做菜/上菜经营 | 现有双人经营首版可继续打磨 | 制作/商店可借原作；自营顾客、案板、上菜、结算仍需定制 | 模组不天然自带戴夫式经营循环 |
| 筏随海流航行、逐格扩建、设施与角色同行 | 现有世界模型已支持，能统一控制碰撞/交互 | 可能需要自定义移动区域或位置模型，并处理玩家/设施/保存同步 | 深度定制，不能只用新地图代表全部功能 |
| 水下横版视角、鱼叉动作、敌人冲刺与返航 | 当前已用独立水下场景/规则实现 | 可借代码模组实现，但渲染、控制、碰撞与状态转换要专门适配 | 模组可行性需实测，不能断言不可能或零成本 |
| 两人一人潜水一人甲板/岛上 | 主机裁决和分场景已存在，本机通过；邀请/跨电脑仍有缺口 | 原生会话、分地点同步、SMAPI消息可复用；横版/动态筏的状态还要验证 | 联机基础是Mod的复用收益，新增规则仍需实测 |
| 到手可玩与维护 | 独立exe直接运行，所有内容/性能/音效问题由项目承担 | 依赖本体、SMAPI和所需模组，需固定兼容组合 | 更少底层工作，增加上游更新/模组组合维护 |

## 现有成果能复用多少

当前是Godot 4.7.1、GDScript、ENet与自定义v16保存。代码模组运行在星露谷/SMAPI的C#环境，`world_state.gd`、Rooms、Godot界面和ENet协议不能原封不动执行；切换路线属于移植产品规则与内容，而非给exe包一层模组。

可作为迁移输入的有：`docs/narrative`人设/关系/节点/对白；作物/配方/委托的设计表；已有测试用例和交互规范；适用使用条件的原始图片。运行时数据结构、坐标/地图碰撞、UI与输入、保存和联机需要重新适配。现有存档没有现成一键转换方案。

即便继续独立开发，也应只实现本作必要的生活规则，复用可兼容模块与素材，不以“把星露谷所有机制都重做一遍”为目标。用户确认的朋友素材授权记录继续保留；本轮未引入新模组素材或代码，未来实际复用按各来源记录，不把某个仓库有源码等同于全部内容可任意复用。

## 哪种选择适合当前目标

选择独立游戏的条件：

- 实际Mod试验表明木筏/横版与原作框架的桥接成本超过复用收益，或产品必须脱离星露谷本体。
- 希望独立启动、控制完整操作与视觉，愿意承担地图布景、人物动作、UI、音效和内容数量的长期打磨。
- 接受先做有密度的小范围内容，不按原作完整体量追赶。

选择模组的条件：

- 最想要的是马上拥有成熟农事、城镇生活和丰富NPC，再添加中国人物、岛屿和经营故事。
- 可以接受原作生活/时间与操作框架，并且代码Mod小样能以可维护的方式保留海上核心；若需要简化核心，必须另作明确取舍。
- 接受玩家安装本体及依赖，维护一组确定的兼容版本。

**当前建议不同时开发两个完整项目，也不立刻丢弃0.18。** 先讨论上述证据与最小隔离试验；当前用户没有选择迁移，本次只有研究与设计。人物风格已确认近代中国海港，可以跨路线复用设计，但暂不据此批量替换素材。

## 如需模组试验，只验证最难的问题

不是再做一个种田示例来证明原作会种田。建议在独立测试档/目录中验证：

1. 两人可分别留在甲板与横版水下；时间、暂停、氧气和返回不互相强制传送。
2. 一条抛出/漂浮/收回的钩子沿途取得多物，重复消息不重复奖励，容量不足不吞物。
3. 筏移动时人物、箱子与扩建格相对位置正确；甲板改变后保存、退房、重连还能一致恢复。
4. 接一个小岛入口和一个NPC对白，看新场景如何与原作日程/保存共存。

若以上核心环节都需大量侵入式补丁，模组节省的农事工作可能被海上改造抵消；若接受原作俯视潜水/固定船区后实现明显更简单，则模组方案更值得推进。这是待验证判断，当前不报保证工期，也未声称任何现成模组组合已达到这些要求。
